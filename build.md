**Deviations from brief — two blockers hit, both resolved, details below:**

1. **`DATABASE_URL`'s original host (`mk7ayr3frijitxqkgo2a29hm`) is a
   Coolify-internal Docker hostname — unreachable from a local dev
   machine.** Confirmed via `Test-NetConnection` (TCP + ping both failed)
   before touching anything else. Asked you how to proceed; you chose to
   expose a public port in Coolify. That produced `182.8.97.66:5433`,
   which *also* didn't connect (confirmed both via `Test-NetConnection`
   and by checking, on the server itself, that `ufw` allowed `5433/tcp`
   and that `docker-proxy` was bound to `0.0.0.0:5433` — both were
   already correct, so the block was upstream of the box, not on it).
   **Resolution:** you're on the same Tailscale tailnet as the server
   (`casper`, `100.101.248.124`) and this dev machine already had
   Tailscale running — routing through the Tailscale IP instead of the
   public IP worked immediately. `DATABASE_URL` in `.env` now uses
   `100.101.248.124:5433`. **This is a local-dev-only detail** — once
   the API is deployed to Coolify (Phase 6), it'll run inside Coolify's
   own network and should go back to the original internal hostname, not
   Tailscale or the public port. Documented in README under "Reaching
   the database from your local machine" so this doesn't need
   re-diagnosing next session.

2. **`prisma migrate dev` failed on the second (GIST index) migration**
   with `type "geometry" does not exist`, even though the first migration
   had just succeeded. Root cause: `migrate dev` validates migration
   history by replaying it against a disposable shadow database, and
   that shadow DB doesn't have the PostGIS extension enabled — so
   replaying the `init` migration's `geometry(...)` columns there fails.
   (The *first* migration didn't hit this because there was no prior
   history to replay yet.) **Resolution:** hand-authored the migration
   folder/file instead of using `--create-only`, then applied it with
   `prisma migrate deploy`, which applies pending migration files
   directly with no shadow-database step. Documented as a "known gotcha"
   in the README so future raw-SQL migrations in this project use
   `deploy`, not `dev`, from the start.

## Phase 4B — MAPID basemap integration + Playwright verification
Added to plan 2026-08-21 (not started). Not part of the original brief —
requested as a correctness check before building further UI-adjacent work.

**Purpose:** confirm the MAPID basemap itself (tiles/SDK, using
`MAPID_API_KEY`) correctly renders our geodata — not a real frontend, no
styling effort. Just: do the dots land in the right place.

**Scope:**
- A minimal standalone HTML test page (no framework) that loads the MAPID
  basemap and plots, for all 7 stations:
  - the station point itself
  - its isochrone polygon (from `GET /api/stations/:id/isochrone`)
  - the POIs inside that isochrone (from `GET /api/stations/:id/pois`)
- Drive that page with the Playwright MCP: load it in a real browser,
  read back rendered marker positions, and assert each station marker
  matches its known `stations.geojson` coordinate (within a small
  tolerance), the isochrone polygon actually renders, and POI dot count
  on the page matches the API response count.
- Explicitly out of scope: layout, styling, any production frontend
  component — this is a correctness harness, not a deliverable UI.

**Blocked on:** Phase 3 (need real station/isochrone/POI rows in the DB —
this can run against a partial dataset, doesn't need every ingestion
script done) and Phase 4 (needs the isochrone/pois GET routes live
locally).

**Open question, not yet resolved:** the brief and the MAPID API
reference block only cover the Missions/Activities competition
endpoints — there's no confirmed spec yet for the MAPID *basemap*
product itself (tile URL scheme, JS SDK vs. plain XYZ tiles compatible
with Leaflet/MapLibre, whether `MAPID_API_KEY` is the right credential
for tile requests or basemaps use a separate key). Will ask before
writing the test page rather than guessing at an integration shape.
