## Phase 9 — AI-generated station insights
Added to plan 2026-08-23 (not started — explicitly deferred until after
Coolify deployment finishes, per the project owner's own sequencing).
This is the reason `ANTHROPIC_API_KEY` exists in this project at all,
beyond `classify-categories.js` — a real, planned product feature, not
an afterthought.

**The feature, as described by the project owner:** the eventual
frontend needs AI-generated natural-language insights per station —
"if you go to this station, expect X," "this area is known for Y" —
grounded in the station's real data (POIs, categories, price
distribution, etc.), with some room for the AI to add color/fun facts
but "don't go too much outside the API" — i.e., stay grounded in real
data, not free-form hallucination.

**Terminology clarified in conversation:** the project owner asked
about a `skill.md` for this — that's a Claude Code-specific concept
(how *this* CLI tool behaves) and doesn't apply to a deployed app
talking to the Anthropic API directly. The actual equivalent for this
feature is a **system prompt** — a versioned, readable document
defining the AI's role, what data it's given, and how much creative
latitude it has. Plan: `backend/ai/station-insights-prompt.md`
(exact path TBD when this is built), not just a string buried in route
code.

**Recommended architecture (not yet built, for discussion when this
phase starts):** the backend fetches the station's real data itself
(reusing the same aggregation `/api/stations/:id/context` already
computes) and makes **one grounded Claude call** with that data
stuffed into the prompt, returning the generated text. Explicitly
**not** an agentic design where Claude gets live tool-access to call
the API itself and decide what to fetch — that would be slower, far
more expensive per request (multiple model turns instead of one), and
harder to keep grounded/predictable. A single-call, data-in-prompt-out
design fits both the project's Anthropic budget (~$5, discussed
earlier this project) and a hackathon timeline much better.

**Real open questions, not yet answered — needs a decision before
building, not blocking documentation of the plan right now:**
1. **Caching/generation strategy** — should this call Claude live on
   every single request to a new route (e.g. `GET
   /api/stations/:id/insights`)? That's a real cost and abuse-surface
   risk for an unauthenticated public endpoint — anyone could hit it
   repeatedly and run up API spend with no rate limit. Alternatives:
   generate once per station (or per station+minutes combo) and cache/
   store the result (e.g. a new nullable column or small table,
   regenerated by a standalone script like the existing
   `classify-categories.js` pattern, not on-demand per request); or add
   real rate-limiting to a live-generation route if on-demand freshness
   actually matters.
2. **Exact scope of the prompt's data** — full `/context` payload
   (category counts, price distribution) plus the raw POI list (names,
   menu_utama, jam_buka, etc.)? Or a curated subset? More data in the
   prompt costs more tokens per call.
3. **"Fun facts" boundary** — the project owner explicitly wants some
   room for the AI to add color beyond the raw API data, but "not too
   much." This needs a concrete instruction in the system prompt (e.g.
   "you may note well-known general facts about this area of Jakarta,
   but never invent a specific business, price, or amenity not present
   in the data provided") — worded precisely when this phase starts,
   not left vague.
4. **Model choice** — same reasoning as `classify-categories.js`
   applies: this is a bounded, structured-ish generation task (not deep
   reasoning), so `claude-haiku-4-5` is the likely right default for
   cost, unless generated-text quality at Haiku tier turns out to feel
   noticeably worse than Sonnet for user-facing copy — worth an actual
   side-by-side comparison before deciding, not assumed.

"the AI would be fed the endpoints of the domain later after its done
deploying") — start this phase once the API has a real public URL.

(`https://mapidapi.darrencasper.com`), so this phase was built end to

All 4 open questions from the plan above resolved:
1. **Generation strategy:** pre-generated/cached, confirmed via
   discussion — not live-per-request.
2. **Prompt data scope:** `poi_count_by_category` +
   `price_distribution` (same shape `/context` already computes, reused

3. **"Fun facts" boundary:** written precisely into

4. **Model:** `claude-haiku-4-5`, confirmed appropriate — verified with

**Files created:**
- `ai/station-insight-prompt.md` — the system prompt as a standalone,
  readable document, not a string buried in code.
- `lib/generateStationInsight.js` — pure generation function (one
  Claude call, returns text, does not touch the DB) plus
  `generateAndSaveInsight()` (generate + persist), the latter reused
  identically by the script, the admin route, and the scheduler so the
  `UPDATE` statement exists in exactly one place.
- `scripts/generate-station-insights.js` — three modes: no args (only
  stations whose data changed — the smart default), a `station_id` arg
  (force that one), `--force-all` (force every station regardless of
  staleness, for e.g. a prompt-wording change that should apply to
  everything).
- `routes/gis.js`: `GET /stations/:id/insights` — public, reads the
  cached column only, never calls Claude.
- `routes/admin.js`: `POST /stations/:id/regenerate-insight` —
  moderator-only (the one route in this app where a request triggers a
  paid API call, deliberately gated behind auth).
- `lib/scheduleInsightRefresh.js` — daily `node-cron` job (03:00 server
  time) running **inside the existing server process**, not a separate
  Coolify scheduled-task feature or host cron entry — portable across
  hosting platforms, calls the same change-detection query as the
  script's default mode.

**Schema additions, two migrations:**
1. `20260823110000_station_ai_insight` — `Station.ai_insight` (text),
   `ai_insight_generated_at` (timestamp).
2. `20260823120000_poi_timestamps` — `Poi.created_at`/`updated_at`, the
   latter maintained by a **real Postgres trigger**, not Prisma's
   `@updatedAt` (which only fires on Prisma Client writes — nearly every
   write to `Poi` across this project goes through `$executeRaw` because
   of the geometry column, across four different scripts; a DB-level
   trigger is correct regardless of which script performs the write,
   without needing to remember to set the column by hand in four
   places). **Verified the trigger actually fires**, not just trusted
   the SQL: updated one row, confirmed `updated_at` changed and
   `created_at` didn't.

**Change-detection query** (`getStationsNeedingInsightRefresh()` in
`lib/stations.js`): a station needs refresh if `ai_insight IS NULL` or
if any POI inside its 15-min isochrone has `updated_at` newer than the
insight's `generated_at`. **Tested both directions, not just the happy
path:** confirmed it correctly returns empty right after a full
generation, and confirmed it correctly detects exactly one affected
station (and only that one) after manually touching a single POI row
near Sudirman.

**A real bug caught before it could cause confusion later:** immediately
after adding the `created_at`/`updated_at` columns, the change-detection
query reported **58 stations as stale** — despite nothing having
actually changed. Traced the cause rather than dismissing it: adding a
column with `DEFAULT now()` to a table with existing rows backfills that
default onto every existing row at the *migration's* execution time —
which happened to run after the initial bulk-generation pass, so most
stations' POIs ended up with an `updated_at` newer than their
`ai_insight_generated_at` purely as an artifact of migration ordering,
not real data drift. Fixed by resetting `ai_insight_generated_at = now()`
for all 90 stations **without re-calling Claude** (the existing text was
still accurate — only the tracking baseline needed to catch up),
verified the stale count dropped back to 0 afterward.

**Generation cost, actual (not estimated):** bulk-generated all 90
stations, 0 failures. Spot-checked output quality and grounding directly
against real data, not just skimmed for plausibility — confirmed
specific place names the model mentioned (e.g. "Pasar Jangkrik," "Pasar
Lokomotif" for Jatinegara) are genuine POIs in the database (from the
Phase 8 Jakarta market data), and confirmed the model is honest about
thin coverage rather than inventing content (Cakung's insight
correctly says options are sparse, matching its real near-zero POI
count).

**Known limitation, not fixed:** at junction/high-density areas
(central Jakarta stations very close together, e.g. Sudirman/Karet/
Tanah Abang), a single POI's `updated_at` can trigger a refresh for
just its own containing station — correct — but doesn't account for
whether the SAME physical change should also be visible to a
neighboring station whose isochrone overlaps. Not addressed; each
station's staleness is evaluated independently, matching how every
other per-station query in this project already works (isochrones
overlapping and being evaluated independently is an established,
accepted pattern here, not new to this feature).

**Deployment note — the live container does not have this code yet.**
Everything above ran against the real production database (same
Postgres instance the deployed app uses), so the schema and data are
already correct in production. But the *code* (new routes, the
scheduler, the updated `/context` route) only exists in this local
working tree until it's committed, pushed, and Coolify redeploys the
container. The public
`https://mapidapi.darrencasper.com/api/stations/:id/insights` route

**The safeguard, as described:** before spending a Claude Haiku call on

(`gpt-5.4-mini` was named) whose only job is deciding "is this actually

Haiku if the guard flags it; only proceed to the real (grounded,

real, legitimate pattern (a cheap classifier gate in front of a more
capable/expensive model), not overengineering.

**Real open questions, not yet answered:**
1. **`gpt-5.4-mini` needs verification, not assumption.** I don't have
   live-verified OpenAI model IDs/pricing the way the `claude-api`

   confirm the exact real model ID (OpenAI's current naming may not

2. **New provider setup from scratch.** This needs a real

   unlimited AI-call exposure. A chatbot can't be pre-cached the same

5. **Guard-model failure mode.** If the OpenAI call itself fails

## Phase 11 — Bulk POI ingestion, more coverage for sparse stations
Added to plan 2026-08-23. **Google Places API researched and ruled out
2026-08-23** — real findings below, not a guess. Motivation stands:
Haiku's recommendation quality is limited by real POI density per
station, and several stations (Cakung, Catang, and others — see
Phase 3/7/8 notes) are genuinely thin right now.

**Google Places API: researched directly against Google's own
documentation and current pricing page, ruled out.**
- **ToS is a hard blocker for the plan as originally described**
  ("fetch once, store forever"), confirmed directly from Google's
  Places API policy page: only `place_id` is exempt from caching
  restrictions and may be stored indefinitely — every other field
  (name, address, category, coordinates, hours, ratings) is explicitly
  prohibited from being cached/stored beyond Google's allowed
  exceptions. This isn't ambiguous or a risk-tolerance judgment call;
  it's the specific use case the policy exists to prevent. No pricing
  tier or budget changes this.
- **Cost, for completeness (though moot given the ToS finding):** real
  current pricing pulled from Google's own pricing page — Nearby
  Search Pro $32/1,000 requests (5,000/month free), Place Details
  Essentials $5/1,000 (10,000/month free), Place Details Pro $17/1,000
  (5,000/month free). At this project's actual scale (90 stations),
  usage would likely have stayed within Google's free monthly caps —
  cost was never actually the blocking issue here, the licensing was.

**Alternative found and recommended: Overture Maps Foundation.** Free,
Apache 2.0-licensed open POI dataset (Linux Foundation project, data
assembled from multiple contributors including Foursquare), explicitly
designed for downloading and storing in your own database permanently
— no per-request cost, no caching-duration restriction, the direct
opposite of Google's terms for this exact use case. Every other
commercial alternative checked (Foursquare Places API, HERE, Yelp
Fusion, TomTom, Mapbox Search, LocationIQ) has its own version of the
same permanent-storage restriction Google has, to varying degrees —
Overture and raw OSM data (which this project already uses) are the
two genuine exceptions.

**Revised plan, two parts, in order of effort:**
1. **Expand existing OSM/Overpass tag coverage first** — zero new
   integration, infrastructure already built and proven working
   (`fetch-osm-fallback.js`, `fetch-osm-entertainment.js`). More
   amenity/shop categories could meaningfully help the sparse stations
   before reaching for an entirely new data source.
2. **Overture Maps Places dataset** for genuine additional density
   beyond what OSM has mapped — new script
   (`fetch-overture-places.js`), same shape as every other Phase 3/8/11
   ingestion script: `ST_Contains`-boundary verification (don't trust
   an external source's own spatial filtering, same lesson learned
   from both Overpass and would-be Google integration), case-insensitive
   dedup, explicit category-mapping lookup table (not a guess-based
   classifier), new `PoiSource` value (e.g. `overture_maps`) for honest
   provenance — same pattern as `jakarta_opendata`.

**Not started — no code written yet for either part.** Ruling out
Google Places was the main open question for this phase; the revised
plan above is ready to build whenever this phase is picked up.
